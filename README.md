# FinConvBench v1.0

FinConvBench is a benchmark for message-level language identification of short banking messages in English, Hindi, Tamil, Telugu and Kannada, in native script and in romanized (Latin-script) code-mixed form.

It accompanies the paper:

> Piyush Agarwal. *FinConvBench and FinConvLID: Benchmarking Message-Level Language Identification for Romanized Indic Code-Mixed Banking Conversations.* 22nd International Conference on Natural Language Processing (ICON 2026).

## The data is synthetic

Every message was generated by a large language model (Claude Sonnet 4.5), passed through programmatic noise injection (casing, typos, abbreviations, punctuation), and then audited. It contains no customer data and no production data. Scores on it measure agreement with the labeling convention described below. They are not evidence of performance on real bank traffic.

### `data/FinConvBench_v1.0.csv`

| Column | Meaning |
|---|---|
| `id` | Row identifier, 1 to 11465. |
| `text` | The message. |
| `expected_language` | The audited label (see below). |
| `category` | Banking intent category (25 values, such as `balance_check`, `card_block`). |
| `noise_type` | One of `clean`, `caps`, `typo`, `polite`, `urgent`, `variant`, `abbreviation`, `contextual`. |
| `difficulty` | `easy`, `medium` or `hard`, as tagged at generation time. |

Labels and row counts:

| Label | Meaning | Rows |
|---|---|---:|
| `hi-en` | Romanized Hindi, usually mixed with English | 3,333 |
| `ta-en` | Romanized Tamil, usually mixed with English | 1,596 |
| `te-en` | Romanized Telugu, usually mixed with English | 1,591 |
| `kn-en` | Romanized Kannada, usually mixed with English | 1,589 |
| `en` | English | 1,486 |
| `hi` | Hindi in Devanagari | 500 |
| `unknown` | No usable language signal | 468 |
| `kn` | Kannada in Kannada script | 302 |
| `te` | Telugu in Telugu script | 300 |
| `ta` | Tamil in Tamil script | 300 |

The `-en` suffix tracks script and register, not the presence of English words. A message in pure romanized Hindi is `hi-en`.

### `audit/label_audit_record.csv`

| Column | Meaning |
|---|---|
| `id`, `text` | The benchmark row. |
| `old_label` | The label before the audit. |
| `new_label` | The label after the audit. It equals `expected_language` in the benchmark file. |
| `decider` | `auto_bucket_A` (4,422 automatic decisions), `english_review_override` (21), `human_accept` (10) or `human_custom` (1). |
| `reason` | The rule or the reviewer's note. |

## Scoring

The paper excludes the 468 `unknown` rows and scores the remaining 10,997.

- **Exact-label accuracy:** the predicted label equals `expected_language`.
- **Reply-language accuracy:** the language the assistant would reply in is acceptable for the message. Hindi messages (`hi`, `hi-en`) accept a reply in `hi` or `hi-en`. All other messages accept a reply in `en`. This encodes one product decision (Tamil, Telugu and Kannada users receive English replies), so the metric is relative to that policy.
- **Label-in-family:** the predicted label has the same base language as the benchmark label (`ta` and `ta-en` are one family).

`score.py` computes all three. It needs Python 3 and nothing else.

```
python3 score.py predictions.csv
```

`predictions.csv` has a header row and the columns `id` and `predicted_label` (one of the nine labels above; anything else is scored as wrong). The script derives the reply language from the predicted label: the label itself if it is `hi` or `hi-en`, otherwise `en`. This is the rule the paper applies to the baseline tools. If your system chooses its own reply language, add a third column `reply_language` and the script uses it instead; FinConvLID's reply score in the paper is computed that way.

Part of the benchmark (its Latin-script rows) was used to train the small fastText classifier inside FinConvLID, so the paper's in-domain scores include training rows. The paper also reports a rescoring on rows with no text overlap.

## What is not included

The FinConvLID implementation, its trained checkpoint and the detailed evaluation records are private and are not part of this release. `score.py` only compares labels; it contains no part of the detector.
